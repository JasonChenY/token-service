token-service · 作为 OAuth2 Resource Server 的架构

RS 模式 RFC 6750 / 9728 / 8414 / 7662 STS AssumeRole

开启 OPENID_RESOURCE_SERVER=true 后，token-service 成为标准 OAuth2 资源服务器。 核心是三方协作：MCP 客户端/Agent ↔ token-service（RS） ↔ Keycloak（AS）， 再加腾讯云 STS。服务只做「验明身份 → 换取角色临时凭证」的桥接。

3关键设计点

环节做法对应代码
端点发现 只配 AS issuer，introspection / authorization 等端点全部从 .well-known（OIDC discovery → 回退 RFC 8414）动态拿，不硬编码厂商路径 as_metadata()
401 挑战 无 / 无效 token 返回 WWW-Authenticate: Bearer resource_metadata=…（RFC 6750 + 9728），引导客户端自行发现 AS unauthorized()
token 校验 RS 用机密 client（client_secret_basic）调 introspection（RFC 7662），不自己验签 introspect_token()
错误码区分 401 TokenInvalid 客户端重新登录；502 ASUnavailable 上游故障，不误导登录 resolve_username_rs()
身份映射 username 取自 introspection 响应 preferred_username，作为 STS RoleSessionName（审计用） username_from_claims()
缓存 进程内按 (session_name, duration) 缓存，临期（REFRESH_MARGIN_SECONDS）前自动重签 get_credentials()
阻塞下放 introspection 与 AssumeRole 均为阻塞网络调用，anyio.to_thread 下放线程池，不堵事件循环 credentials() / get_temporary_credentials()
一句话概括 RS 模式的信任链：客户端的身份由 Keycloak 背书（introspection）， 腾讯云的权限由角色 ags-sandbox-role 承载（AssumeRole）。 token-service 只做「验明身份 → 换取角色临时凭证」的桥接，自己不持有也不下发用户的长期密钥。
